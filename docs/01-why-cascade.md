# 01 · 为什么做级联推理

> 系列：When to Speak → **When to Escalate**。前者回答"什么时候该说话"，后者回答"什么时候该升级模型"。

## 1. 问题不在模型，而在单位经济

Agent 产品进入 2026 年后，成本从"工程细节"变成"产品能否成立"的主要变量。行业报告反复给出同一个结论：推理成本不是一个单价问题，而是**路由问题**——把每一个请求都送进最贵的模型，成功率也许最高，但单位经济会先崩。

级联推理（cascade inference）的假设很朴素：

- 大多数任务并不需要旗舰模型；
- 小模型做错时，我们通常能感知到（失败、超时、置信度低）；
- 因此可以先让小模型尝试，只有"不确定"时才为旗舰付费。

Perplexity 的 Portable Computer、RouteLLM 的路由实验、LiteLLM 的 fallback 链，本质上都在表达同一件事：**不是所有任务都值得用最贵的模型**。

## 2. 三种架构，同一任务流

| 策略 | 行为 | 直觉 | 典型问题 |
|---|---|---|---|
| `all_frontier` | 所有任务都走旗舰 | 省心、成功率高 | 成本高，重度用户毛利恶化 |
| `cascade` | 小模型先做，失败或低置信才升级 | 按需付费 | 需要可信的升级信号 |
| `all_small` | 全部下沉小模型 | 成本最低 | 复杂任务失败，重试也会花钱 |

只看"单次调用价格"会得出错误结论：

- 全旗舰的单次价格高，但没有重试浪费；
- 全小模型的单次价格极低，但复杂任务的失败成本要摊到成功任务上；
- 级联同时承担小模型成本与部分旗舰成本，但**只对真正需要的任务**支付旗舰溢价。

所以本项目的北极星指标不是"平均单价"，而是 **Cost per Successful Task（CPST）**：成功任务的总成本 ÷ 成功任务数，失败与重试的浪费都算进去。

## 3. 这个项目要证明什么

本项目是一个可运行、可服务化的产品原型，而不是一篇观点文章。它要证明三件事：

1. **路由与账本可以做成纯函数。** 给定任务、定价和策略，成本、置信度、升级链完全可复现，不依赖 GPU 或在线服务。
2. **级联可以在成功率不下降的前提下显著降本。** 在 100 条合成任务与示例定价下，mock 账本显示级联相对全旗舰节省约 **49.87%**，成功率从 98% 升到 99%。
3. **单位经济可以变成可交互的产品界面。** 面板允许访客切换三种策略、调整阈值与单价、逐任务查看升级原因，并可选连接真实网关。

同时，项目明确**不证明**：

- 真实模型上的成本/质量结论（F2.5 需要 GPU 与旗舰 endpoint，目前 blocked）；
- 学习型路由器的效果（本期只用确定性规则）；
- 任何厂商的真实报价（定价表是示例值）。

## 4. 设计原则

- **Mock 优先，真实可选。** 没有 GPU、没有 API Key 也能完整跑通账本、网关单测和静态面板。
- **确定性。** 固定种子、稳定哈希、纯函数计算；同输入同输出，便于验收与回归。
- **每次尝试都记账。** 失败、重试、升级都不是"免费"的，必须进入 CPST。
- **一个口径。** Python 账本与浏览器面板共用同一套公式，并通过 `verify_web_metrics.js` 强制对齐。
- **零密钥交付。** endpoint 与 key 只走环境变量；静态站点默认不发起任何网络请求。

## 5. 与 When to Speak 的关系

两个项目共用同一套 Harness Engineering 工作方式：

- `AGENTS.md` / `harness.yaml` / `init.sh` 定义会话如何开始与验收；
- `private/` 保存本地状态（gitignore），公开仓库只放可复核的 feature list、进度与文档；
- M1 → M2 → M3 严格顺序，一次一个 feature，evidence 可复核才标 passing。

叙事上，When to Speak 处理"交互时机"，When to Escalate 处理"算力层级"。两者都是 Personal AI / Always-on Agent 的基础设施问题。
